设置界面一行都不用改。


三、界面
----------------------------------------------------------------
26.x 是"提取式 GUI"：覆写 render() 能编译通过但永远不会被调用，
必须覆写 extractRenderState(GuiGraphicsExtractor, ...)。本模组按此实现。

布局完全由可用高度推导，不写死像素：

  titleBlockHeight = 标题实际行数 × 行距 + 语言按钮（放不下时额外占一行）
  available        = height - titleBlockHeight - FOOTER_HEIGHT
  rowHeight        = max(12, available / 行数)
  lineBudget       = rowHeight / LINE_STEP            （每行可容纳的文本行数）

每一行按 lineBudget 决定画几行文本，所以窗口再矮也不会出现行压行：
  3 行：中文名 / 英文名 / 描述（描述过长时自动换成两行）
  2 行：中文名 / 描述
  1 行：中文名

文本宽度用 Font.plainSubstrByWidth 量出再加省略号，而不是用剪刀裁剪——
剪刀会把字符切成两半。

语言按钮先尝试缩窄以放在标题右侧；窄到 64px 仍放不下时才移到标题下方。
这是唯一会移动位置的控件，且移动由可用宽度决定，不是硬编码。

界面 isPauseScreen() 返回 false：世界继续运行，才能在界面里观察冷却计时。


四、功能一实现（锁定窗口大小）
----------------------------------------------------------------
全部 SDL 调用集中在 GameWindowLock，三个机制叠加：

1. SDL_SetWindowResizable(handle, false)
   去掉 WS_THICKFRAME，这是边框能缩放的根源；同时双击标题栏不再最大化。

2. SDL_SetWindowMinimumSize / SDL_SetWindowMaximumSize 都设成锁定时的尺寸
   让操作系统层面也无法改变窗口大小。

3. 每个客户端 tick 调 enforce()，读回窗口位置，与锁定值比较，不同就写回。
   Windows 在按住标题栏时进入系统级 modal move loop，外部无法取消，
   所以拖动过程中窗口会跟随，松手后立刻被拉回。最终状态恒等于锁定位置。

保护条件:
  · 全屏 / 最大化 / 最小化时不做纠正 —— F11 是玩家的正当操作，不能对抗。
  · correcting 静态标志防止自己的写入再次触发纠正（无限递归）。
  · 窗口 handle 为 0 时拒绝启用，并把 applied 置回 false，
    不让开关出现"显示开启但实际没生效"的状态。

关闭时反向恢复: Resizable(true)、最小尺寸回 320×240（原版值）、
最大尺寸回 0xFFFF（SDL 的"无上限"）。三个值都必须恢复，
只恢复 resizable 会留下一个隐形的尺寸上限。


五、功能二实现（烟花冷却）
----------------------------------------------------------------
关键判断: MultiPlayerGameMode#useItem 在方法内部就把包发给服务器了，
所以在 RETURN 注入再改返回值是"已经发出去了才拒绝"，等于无效。
必须注入 HEAD 并 cancel，才能让这次点击根本不产生。

  @Inject(method = "useItem",   at = @At("HEAD"), cancellable = true, require = 1)
  @Inject(method = "useItemOn", at = @At("HEAD"), cancellable = true, require = 1)

两条都要拦，因为烟花火箭有两条使用路径（空中加速 / 对地面放置）。

返回 InteractionResult.FAIL：它的 consumesAction() 为 true 而不代表成功，
正好表示"这次点击已被吃掉、不要有任何后续反应"。

计时用 System.currentTimeMillis() 而不是 tick 计数：
客户端卡顿时两次点击可能落在同一 tick，而卡顿正是玩家连点的场合。
同时给客户端冷却表 addCooldown(60 tick)，让物品栏显示原版冷却动画。

require = 1 是有意的：将来版本若改了方法名，游戏会在启动时直接报错，
而不是让开关静默失效。


六、功能三实现（下雨就可以睡觉）
----------------------------------------------------------------
26.3 把"能不能睡"这一条从方法里的判断抽成了数据：睡眠前先问
BedRule.canSleep(Level)，规则是 WHEN_DARK 时它会调用 Level.isDarkOutside()。
也就是说，白天不能睡是因为"天不黑"，而不是因为"不是夜晚"。

因此只要让 canSleep 在"下雨 + 开关开启"时返回 true 即可：

  @Inject(method = "canSleep", at = @At("RETURN"), cancellable = true, require = 1)

选择 RETURN 注入而不是 HEAD，有两个原因：
  · 只在原版已经判定为 false 时才有机会改成 true，永远不会把"允许"改成"拒绝"；
  · 规则对象是共享的（BedRule.CAN_SLEEP_WHEN_DARK 是静态常量），改规则本身
    会污染全局，改一次调用的返回值则不会。

注入点放在公共源集（mixin/MixinBedRule），因为 canSleep 由服务端和客户端
都会调用；只放客户端会导致单人游戏的整合服务端不生效。

下雨判定用 level.canHaveWeather() && level.isRaining()：前者排除下界/末地
（这两个维度没有天气，行为必须保持原版），后者用原版自己的阈值
（rainLevel > 0.2），不自己另定标准。

"跳到第二天"没有自己实现：原版在玩家入睡后，由 ServerLevel 的睡眠逻辑
调用 moveToTimeMarker(..., WAKE_UP_FROM_SLEEP) 推进时间。我们只放行"能不能睡"，
后续完全走原版，所以不会出现"睡了但天没亮"或"跳过时间的方式和原版不一致"。


七、功能四与功能五的实现
----------------------------------------------------------------
两个功能都是"拦掉一个动作"，但要在正确的层次上拦。

Q 键丢弃:
  Minecraft.handleKeybinds 里读 keyDrop，然后调用
  MultiPlayerGameMode.dropItem(LocalPlayer, boolean)。
  这个方法内部做了两件事: 从背包移除物品、发送 ServerboundPlayerActionPacket。
  两件事都在方法体内，所以必须在 HEAD 取消；在 RETURN 取消的话物品已经
  从客户端背包里消失了。
  参数 boolean 同时覆盖普通丢一个和 Ctrl+Q 丢整叠，一个注入点即可。

F11 全屏:
  Minecraft.handleKeybinds 里读 keyFullscreen，然后调用私有的
  Minecraft.toggleFullscreen()。而这个私有方法的唯一调用方就是按键处理，
  所以取消它等于只关掉 F11: 视频设置里的全屏按钮、启动参数、
  操作系统快捷键都不经过这里，不受影响。
  必须 HEAD 取消: 方法内部会调整窗口尺寸并重建 framebuffer，
  事后再取消会留下改了一半的显示状态。

两个判定都写成 DropKeyRule / FullscreenKeyRule 里的纯布尔函数，
所以有单测覆盖"开关打开时拦、关闭时放行"这两条。

八、功能六的实现（关闭药水粒子）
----------------------------------------------------------------
26.3 里药水粒子是这样产生的: 实体身上的 MobEffectInstance 通过
MobEffect.createParticleOptions 生成 ParticleOptions，存进同步数据
DATA_EFFECT_PARTICLES；客户端在 LivingEntity.tickEffects() 里读出这个列表，
按概率调 Level.addParticle 把它变成真正可见的粒子。

拦截层次的选择:
  · 不去碰 MobEffectInstance / DATA_EFFECT_PARTICLES —— 那是效果数据本身，
    改它会连带影响效果的同步与判定，风险大且违背"不影响效果"的要求。
  · 也不在粒子引擎里过滤列表 —— 那是每帧遍历，代价高。
  · 改在 ClientLevel.doAddParticle 的 HEAD 取消，一次判断即可，
    而且这是两个公开 addParticle 重载共同的落点，一个注入点覆盖全部。

只按类型过滤: ENTITY_EFFECT（持续生效药水的螺旋）与
INSTANT_EFFECT（瞬间药水的爆裂）。火焰、烟、水花、爆炸、红石等一律放行。

因为只取消了"变成可见粒子"这一步，效果数据、持续时间、等级、
以及服务端的任何判定都没有变——这正是需求里"不影响药水效果"的保证。

运行时已验证: 加 -Dmixin.debug.export=true 后导出的
ClientLevel.class 里，doAddParticle 方法开头确实出现了
handler$xxx$moreswitches$hideEffectParticles 调用并检查 isCancelled。

九、功能七与功能八的实现（模拟光照）
----------------------------------------------------------------
这两个功能都不许改动世界真实光照，所以关键是"只改渲染时读到的东西"。

26.3 里方块面的亮度是这样来的:
  BlockModelLighter → LightCoordsUtil.getLightCoords(BrightnessGetter, 世界, 状态, 位置)
  返回一个打包的 int: sky << 20 | block << 4
  光照贴图只是 (方块光, 天空光) 的二维查找表，与位置无关。

由此得出一个重要结论: 直接去改光照贴图，会让整个屏幕一起变亮，
不可能形成"玩家身边一圈光"。所以移动光源必须在"每个方块位置"这一层做。

功能八（移动光源）:
  参考 LambDynamicLights 的做法（其 BrightnessGetterMixin 用 @ModifyReturnValue
  改 LightCoordsUtil$BrightnessGetter 的 DEFAULT 实现，再由
  ChunkRebuildScheduler 调 Minecraft.levelExtractor.setSectionDirty 触发重建）。

  本模组注入 LightCoordsUtil.getLightCoords 的 RETURN，用模拟值替换该位置的方块光:
      int packed  = 原返回值
      int existing = LightCoordsUtil.block(packed)
      int simulated = 模拟光等级(该位置)
      if (simulated > existing) 返回 LightCoordsUtil.withBlock(packed, simulated)
  withBlock 只替换 block 位、保留 sky 位，所以天空光完全不受影响，
  白天依然是白天，只是手里的火把额外照亮了近处。

  为什么取 max 而不是相加: 原版里光不叠加，两支火把并排不会比一支更亮。
  取 max 同时保证"本来就亮的地方"不会被模拟光照得比模拟光源本身还亮。

  但只改建网格时的采样值不会显示——这些值被烘焙进区块顶点，区块早建好了。
  另一个致命细节: 注入里不能拿传进来的 level 和 minecraft.level 做同一性比较。
  建区块网格时调用方传的是 RenderSectionRegion（区块快照），不是 ClientLevel，
  一比较就永远不相等，于是每次都提前返回，光永远烘焙不进去。
  这正是这一版之前"重建在触发但画面没变化"的原因。

  必须让网格重建: 光源跨方块时，对光源所在区块及其邻居（3×3×3）调用
  Minecraft.levelExtractor.setSectionDirty(x, y, z)。
  注意入口是 levelExtractor，不是 ClientLevel.setSectionDirtyWithNeighbors：
  26.3 的区块网格调度在新的 extract 管线里，走 Level 那条路到不了。
  火把射程 13 < 16，所以 3×3×3 已覆盖全部受影响区块。

功能七（预览光照范围）:
  改为屏幕空间 HUD 绘制，不再走世界空间提交。

  世界空间试过两次都不可见: 每帧确实提交了上万条 submitText，
  但屏幕上一条都没有。先补了相机位移，再用 camera.orientation 做公告板，
  仍然看不到，因此判定这条路径在 26.3 不可靠，改用 HUD。

  现在的做法:
    1. 遍历模拟光源能到达的立方体，筛出"实心、上方是空气、
       且模拟光确实比现有方块光更亮"的方块
    2. 用 ScreenProjection 把每个方块顶面中心投影到屏幕坐标
       （眼睛位置 + 视线方向 + 垂直视场角 + 视口尺寸，纯算术，可单测）
    3. 按距离取最近的至多 320 个，用 GuiGraphicsExtractor.text 画青色数字

  代价是不再做深度遮挡判断，数字会画在方块之上——
  对"光照范围预览"来说这正好是想要的读数效果。

两个功能的共同点: 都只读取设置与位置，从不写入 Level、光照引擎或存档。

十、功能九到功能十一的实现
----------------------------------------------------------------
这三个都属于"阻止原版做某件烦人的事"，关键是找准唯一的触发点。

功能九（关闭资源包警告）:
  原版在启用资源包前问 PackCompatibility.isCompatible()，
  返回 false 就会弹 ConfirmScreen 说"这个包是为其他版本做的"。
  注入 isCompatible 的 HEAD 返回 true，于是走"直接启用"的分支，不再弹框。
  只跳过提示，资源包照常加载；包真的缺失/损坏由另一条存在性检查处理，不受影响。

  补充（第一版漏掉了真正的入口）:
  光改 isCompatible 不够。资源包列表拿的是 Entry.getCompatibility() 返回的枚举值，
  直接和 COMPATIBLE 比较来决定要不要显示"不兼容"标记与确认框，
  并不经过 isCompatible()。所以还要注入 PackSelectionModel$EntryBase.getCompatibility，
  让它返回 COMPATIBLE，这样标记和弹框才会一起消失。

功能十（关闭篝火烟雾）:
  CampfireBlock.makeParticles 是普通篝火、灵魂篝火、干草捆信号篝火共同的
  产烟入口。在 HEAD 取消，一次覆盖全部三种，不必事后按粒子类型过滤。
  火焰（animateTick 里的 LAVA 粒子）不走这个方法，所以仍然保留。

功能十一（关闭新手教程）:
  Tutorial.start() 是教程选步骤的唯一入口，取消后 instance 保持为空。
  这一点很关键: Tutorial 的 tick / onMouse / onInput / onGetItem / stop
  每一个都在开头判空直接返回，所以取消 start 不会引发空指针。
  从源头掐断，比逐个隐藏 TutorialToast 更彻底。

  但"新配方已解锁"不属于教程: 它是 RecipeToast，由
  ClientPacketListener.handleRecipeBookAdd 在收到新配方时调用
  RecipeToast.addOrUpdate 弹出的。所以另注入 RecipeToast.addOrUpdate 的 HEAD，
  让关闭教程的开关同时取消它，配方本身仍然注册、仍在配方书里。

十一、功能十四到功能十六（静音）的实现
----------------------------------------------------------------
三个静音开关共用一个注入点: SoundEngine.play(SoundInstance) 的 HEAD，
命中时返回 SoundEngine.PlayResult.NOT_STARTED，等于告诉引擎这次没播放。

为什么选这里: 声音到引擎有三条路径——服务器发的定位音效包、绑定到实体的音效、
以及像矿车滚动那种长期存在的 SoundInstance。三者最终都汇成 SoundInstance，
在同一处判断即可全覆盖，不必分别拦截 playLocalSound 的两个重载。

匹配用声音标识符（如 minecraft:block.piston.extend）而不是 SoundEvent 对象，
因为 SoundInstance 只暴露标识符；标识符是稳定的资源名，集中写在 SoundRules 里可单测。

爆炸声说明: 原版只有一个 entity.generic.explode 事件，TNT、苦力怕、床、
重生锚共用，因此"关闭爆炸声"必然是关闭所有爆炸声，无法只针对 TNT。

十二、界面滚动
----------------------------------------------------------------
功能从三个增加到五个后，320x180 下每行只剩 20px，只够一行文字，
描述被挤没了。改法是让布局不再"把剩余空间均分给每一行":

  · 行高固定为 PREFERRED_ROW_HEIGHT（名称 + 最多两行描述）；
  · 装不下时不再压缩行高，而是让列表滚动；
  · 只有当窗口矮到连 MIN_ROW_HEIGHT（名称 + 一行描述）都放不下时，
    才继续压缩，然后照旧滚动。

滚动区域（viewport）从标题栏下沿到页脚上沿，行用 scissor 裁剪到该区域，
所以半行永远不会画到标题或完成按钮上。滚动时开关按钮跟着一起移动；
滚出可视区的开关同时置 visible=false 与 active=false，
否则玩家可能点到一个看不见的开关。

滚动条只在内容超出时才画，含轨道、按可见比例计算的滑块、两端箭头；
滚轮滚动一行，点箭头滚一行，点轨道跳到该位置。滑块本身不做拖拽:
拖拽需要一个捕获鼠标的子控件，这个界面刻意没有引入。

单元测试: 30 个（冷却计时 6 + 烟花门控 4 + 雨天睡觉 4 + Q 键 2 + F11 2 +
药水粒子 2 + 光照衰减 7 + 光照规则 3）。
功能九到功能十一没有单独的测试: 它们的判定就是"设置里那个布尔值"，
写一个恒等断言的测试没有价值，改由真机验证注入点。

九、多语言实现
----------------------------------------------------------------
Minecraft 的 Component.translatable 只能跟随游戏语言，无法实现
"游戏英文、模组中文"。因此界面文字走 ModLang：
它在资源重载时用 ResourceManager 读 assets/moreswitches/lang/{zh_cn,en_us}.json，
存成两张表，按界面语言取值；取不到时先回退英文，再回退键名。

同一批 JSON 同时被原版读取（按键名称、分类名），所以文件格式仍是标准格式。
键名一律带 moreswitches. 前缀，避免与其他模组撞键。

关键约定: 每个语言文件只放该语言自己的文本。早期版本把中文放在 name/desc、
英文放在 name_en/desc_en，且两份文件内容完全相同，结果英文界面显示的是
中文描述（截图可见）。现在 zh_cn.json 与 en_us.json 各自只有本语言文本，
行内也不再并列显示另一种语言。

校验方式: tools/check-lang.ps1 按 ModLang 的同一规则打印界面实际会显示的
每一行，并比对两份文件的键集合是否一致；改语言文件后直接跑它，不必开游戏。
